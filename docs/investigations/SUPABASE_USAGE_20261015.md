# Xclip Supabase無料枠調査（2026-10-15 JST）

## 結論と現在の段階

DB移行を直ちに実行する段階ではない。現行のDB取得方法には削減余地があり、無料枠継続を試す価値はある。ただし、現状のまま無料枠へ収まるとの保証はできない。コード静的調査と少量のDB読取測定は終了。本番source/BUILD_ID/対象SHA、実際の再集計頻度、サービス別転送量・ログ内訳を確認してから修正範囲を確定する。

アプリコードの変更・配布・適用はまだ行っていない。今回配布するSH/SQLは読取診断用。DB移行、DB/env/Cron/巡回枠/登録一覧/取得位置/手動削除/学習データの変更はない。PC/UI操作もない。

## 確認できた事実

- ユーザー画像：転送量8.42/5GB、ログ取込2.20/1GB、DB105/500MB、Storage0/1GB。無料枠超過はDB容量ではない。請求サイクルの期間とサービス別内訳は未受領。この画像の累計を1日や1か月の実測速度へ置き換えない。
- ローカルのランキングv2配布対象12ファイルが実コードに一致。本番公開v2静的マーカーも存在。公開マーカーは完全なruntime/source/hash照合の代わりにはならない。本番ソース自体は直前配布物からの既知コードとして調べた。
- 本番向けランキングコードは、表示ごとに現在の安全性・登録有効状態をDBで再確認する。その際、新着1ページ50件の場合も、新着一覧全体最大500件をselect(*)で取得する。分割100IDずつの最大5問い合わせ。ページ数・全件数を現在の安全性に合わせる意図は保持すべきであり、安全確認を省略して通信を減らす案にはしない。
- 一覧editionは5分単位、保存する内容はID・順序・メタデータ。作成時に最近最大1,000件・過去最大3,000件・週間候補等を読む。保存済みeditionを読める場合、作成用の再読取は不要だが、表示用のDB再確認は毎回行う。メモリ内の同時作成まとめは同一プロセス内であり、複数workerでの作成読取重複を完全には防がない。
- 実DBの有効投稿者99件。ランキング候補条件で最近25件・過去1,161件（内容フィルタ適用前）。各8件の標本のみ取得し、1行JSONは約1.38〜1.44KB。投稿本文・ID・URL・未加工応答は保存していない。
- 画像の超過8.42GBに対して、どの処理が何GB使ったかはまだ確定していない。現在の標本は過去のすべての行・時間帯を代表しない。

## 数量試算（請求実測ではない）

- 標本平均と候補件数から、最近・過去候補だけで1回約1.71MB。常時アクセス等で5分ごとに毎回作成する条件なら、30日で約14.75GBのJSON読取相当。週間候補・fallback・表示用再取得は含まない。HTTP圧縮・ヘッダー・課金集計との差があり、請求値として断定しない。アクセスのない時間帯は作成されないので、その時間も毎回作成されたとは扱わない。
- 500件の全カラムを1万回読むと約6.9〜7.2GBのJSON相当。単に表示を50件へ切る現行方式ではDBからの受信量は減らない。
- 選択カラムを絞る概算では標本JSONが約38〜40％減る。ただし試算用の項目一覧は実装の確定仕様ではない。安全判定・順位・手動レビュー・動画再生・視覚モデルの依存項目を照合しないまま削除しない。カラム削減だけで無料枠を満たすとはいえない。
- 5GB/30日は平均約167MB/日。安全余裕を取り、改善後は月4GB相当（約133MB/日）以下を転送量の目安とする。ログは月0.8GB相当以下を目安に測定する。実際の請求期間長に合わせて換算する。

## ログについて

- SupabaseはData APIへのリクエストをAPI Gateway等のログへ記録する。ColorfulBox側のconsole出力を消すだけでSupabaseのログ取込が減るとはいえない。API回数とSupabase側のエラー・サービス別ログを調べる。
- 巡回管理のDB累計件数は投稿者ごとのHEAD count。プロセス内5分キャッシュがあるが、99投稿者ならキャッシュ切れ1回で最大99問い合わせと従来登録読取が発生する。軽い応答でもリクエスト数とログを増やす。画面が常時5分ごとに更新される条件なら約28,512 HEAD/日となるが、実際の画面利用頻度・worker数は未確認。
- 閲覧イベントは1イベントにつきupsertする。DB内dedupeは重複行を防ぐが、同じイベントのHTTP送信自体はなくならない。分析画面は7/30日最大10万行を集計する。これらが主因かはログ件数で確認する。engagement_eventsのデータそのものとSupabaseのログ取込量を同一視しない。
- バックアップのDB読取は転送量へ寄与し得る。ただし実行頻度・実受信量が未確認のため、今回の超過原因をバックアップだけに帰属させない。

## 推奨する削減の順序

1. ランキングで全カラム取得を廃止。表示に必要なデータと現在の安全性・全件数確認を分け、50件のページで全500件の本文・動画URL等を取り直す構造を減らす。非表示/停止/手動除去/手動Tierの反映、正しい全件数、順序固定、24時間・週間との重複除外を回帰検証する。
2. 5分の表示edition作成と、重い候補全件読取を分離。候補を永続キャッシュし、登録・掲載・除外等の更新で失効させる方式を検討する。複数workerでも同時に重い読取が走らない制御を含む。単純な長時間キャッシュでは新規掲載の反映が遅れ得るため、まず更新経路を照合する。安全性は表示時に現在の状態で確認する。更新間隔や画面の意味を無断で変更しない。
3. 管理画面の件数表示をまとめる・要求の重複をまとめる。安全判定や巡回をキャッシュで飛ばさず、表示用件数だけを対象とする。更新時失効・エラーを成功値として保存しないこと・DBごとの分離も必要。
4. ログ内訳でengagement等の割合が大きい場合は、ブラウザ送信前の同じイベントの重複排除、集計結果の短時間キャッシュを追加検討。正当な異なるイベントやセッションを取りこぼさない。原因確認前に分析機能や監視を停止しない。

## 無料継続の判定とDB代替

上記修正後に24〜72時間以上、できれば通常運用の7日間の転送量・ログ増分とアクセス数を比較する。制限中は本来のアクセス量を処理できないため、その低い消費を改善成功と扱わない。請求サイクルのリセットまたは制限解除後の通常負荷を判定に含める。予測が無料枠内で、掲載・監視・除去・学習が維持されればSupabaseを継続。余裕がない場合はPostgreSQL互換の別サービスとColorfulBox MariaDBを、転送量/接続数/費用/成人向けサイトの利用条件/バックアップ/改修量で比較する。まだ特定サービスの契約やDB移行は決めていない。

今月すでに使った転送量は最適化や削除で減らない。無料プランの制限解除時期は警告・請求期間を確認する。猶予/制限の有無は今回の少量読取成功だけで断定しない。
